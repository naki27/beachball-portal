## 総評

1. **古い章と新しい権限表の食い違いが一番多い。** v0.6〜v0.8 で権限・テナント・招待を足したが、§5.6・§5.8・§12 などに「生年月日は管理者のみ」「他チームの選手名は取得できない」といった旧前提が残っている。§3.2 の権限表を唯一の正として、古い記述を寄せる作業が最優先。
2. **マルチテナントの「仕組み」が未完成。** RLS を張る前提なのに `association_id` を持たないテーブルが多い、API パスにテナントがない、協会をまたぐ画面（マイページ・`/api/me`）と「常に 1 テナントずつ」の RLS が両立しない、アプリ用の DB ロールが分かれていない（このままでは RLS が効かない）。
3. **認証は方針は良いが細部に穴がある。** 確認番号の照合を第三者が妨害・消費できる、2 段階認証が未登録・期限切れのときの状態が二重に定義されている、メールアドレス変更がない。
4. **運用の土台が書かれていない。** メール送信のキュー、マイグレーション手順、監視、バックアップの暗号化と保持期間、ログの保持期間、タイムゾーン。
5. **P0 が多すぎて Phase 1a の 4 週は過小。** 優先度表と本文（申込 CSV、年度更新の受付開始、問い合わせフォーム、資料掲示）の食い違いも多い。

## 指摘の一覧（テーマ別）

### A. 権限・テナント分離

- **#1 [高]** §5.6 L615・§5.8 L637・§12 L1874 の「生年月日等は管理者のみ」が、代表者・本人に見せる §3.2 L149-150 と矛盾 → 3 か所を §3.2 に合わせて書き換える
- **#2 [高]** §5.14 L811-812「行がなければ 404」だと、役割のない登録者がテナントの公開ページもチーム作成も使えない → 公開ページとチーム作成・個人登録はログインだけで可、404 になるのは権限付きの資源だけと明記
- **#3 [高]** §5.5 L468「その場でチームを作れる」なのに、申込ページ（§4.2 L213）・§5.6 L605・§10 L1748 は代表者限定 → 入力ページは登録者以上、送信時にチームの代表者か検査。新規作成時はチーム作成と申込を 1 トランザクション
- **#4 [高]** `/` が §4.2 の画面一覧になく、招待メールの「トップの URL」を未ログインで開くと 403、ログインしても協会一覧は空 → `/` と `/mypage` を画面一覧に載せ、招待メールには `/login` か協会トップの URL を載せる
- **#5 [高]** サジェスト（§8.4 L1609・§10 L1773）は他チームの氏名・年代・チーム名を返すが、§3.2 L157・§5.6 L621 は「他チームの選手名を取得できない」 → 二重登録防止の例外として §3.2 に明記し、サジェストは代表者以上に絞る
- **#21 [高]** RLS を張る前提（L821・L1185）なのに、`tournament_categories`・`tournament_documents`・`contact_messages`・`team_members`・`team_admins`・`entry_players`・`entry_audits`・`member_aliases` に `association_id` がない → 全テーブルに追加し、§5.14 の一覧と DDL を一致させる
- **#22 [高]** 子テーブルの外部キーが単一の id 参照で、別の協会の行を指しても DB が拒否しない → 親に `unique (association_id, id)`、子は `(association_id, xxx_id)` の複合 FK
- **#38 [高]** 「テナント外＝404」が「URL のテナントと資源のテナントの不一致」とも「役割の行がない」とも読める → 判定を 2 段で固定。§5.17 L1018・§5.11 L733 の受け入れ条件も合わせる
- **#39 [高]** 「テナント管理者 ⊇ 全チームの代表者」（L132）が、申込フォームの初期表示・マイページ・`/api/me`・「あなたのやること」にも及ぶのか不明 → 包含は認可判定だけ。画面の「代表を務めるチーム」は `team_admins` の行があるチームだけ。管理者として他チームを操作するのは `/admin` 経路のみ
- **#40 [高]** マイページ・`/api/me`・`/invitations`・協会一覧は協会をまたぐのに、RLS は「常に 1 テナント」（L821-823・L860） → 横断画面の一覧を定義し、`user_id` 起点の横断用の読み方（または RLS に `user_id` 条件を併記）を決める

### B. 認証・セッション・2 段階認証

- **#58 [高]** 受け入れ条件 L1728「メール確認番号だけではログインを完了できない」と、L1706・L1729「未登録でも代表者の機能は使える」が矛盾。§9.1 の図に 2 段階目の分岐もない → セッションに段階（email / mfa）を持たせ、図と受け入れ条件を直す
- **#59 [高]** 管理者のセッションが「24 時間で失効」（L1715・L1719）と「管理 API だけ拒否」（L1718・L1730）の二重定義 → 推奨: セッションは全員 10 日のまま、管理権限の行使だけ 2 段階目の確認から 24 時間（運営管理者は 8 時間）で判定
- **#60 [高]** 2 段階目の検査が「管理 API」に限られ、上位が下位を含むルールにより `/api/teams/...` 経由で全チームの個人情報に届く → 管理者としての権限は、2 段階目が期限内のときだけ付与する判定関数に集約
- **#61 [高]** `POST /api/auth/verify` は `{email, code}` だけで誰でも叩けるため、第三者が他人の番号を無効化・ロックできる → 発行時に HttpOnly Cookie で試行 ID を渡し、照合はその試行の番号だけにする
- **#65 [高]** メールアドレスの変更機能がなく、変えると別アカウントが作られて代表者権限・紐づけ・2 段階認証が消える → マイページに変更機能（新アドレスへ確認番号、旧アドレスへ通知）と、運営による付け替え操作
- **#62 [中]** 総当たり対策が【仮】の「メール単位 10 回/時」頼み。番号ごとの 5 回は再送で補充され、同時に有効な番号の数だけ命中確率が上がる → 照合失敗の上限を確定値にし、同時に有効な番号は最新 3 個まで
- **#63 [中]** 再送は 30 秒後から押せるのに発行は 5 回/時（L321・L1668）で、上限到達時の表示が未定義 → 待ち時間を段階的に延ばし、上限時は「◯時◯分まで送れません」
- **#64 [中]** `/api/auth/request` が未検証の `users` 行を無条件に作ってメールを送るため、ゴミアカウントの量産と Brevo の 1 日上限の枯渇を起こせる → `users` の作成は番号入力の成功時まで遅らせ、確認番号メールの全体上限を設ける
- **#66 [中]** 任命直後・リセット直後はメールだけで先に 2 段階目を登録できる。リセット時の本人確認・通知・既存セッションの失効がない → 登録の有効期限、登録・リセット時の通知メール、他セッションの失効
- **#67 [中]** リカバリーコードの生成・再生成、最後の方式の削除禁止、TOTP の確認手順、WebAuthn のチャレンジ API が未定義 → §9.4 に「登録の流れ」を追加
- **#68 [中]** 2 段階目（TOTP・リカバリーコード）の照合に失敗回数の上限がない → 試行 5 回でセッション破棄、ユーザー単位で 1 時間ロック＋通知
- **#70 [中]** ログイン後の「元のページへ戻る」の URL 検証（オープンリダイレクト防止）と Cookie の付け方（`__Host-` など）が未記載 → 戻り先は同一オリジンの相対パスに限定、Cookie 名を固定
- **#71 [中]** 「登録の有無を漏らさない」が request 側だけで、verify 側の応答・所要時間から分かる → verify も同じ応答にそろえる
- **#72 [中・提案]** 2 段階認証のリセット・方式削除・権限解除のときに、既存セッションを自動で失効させるルールがない → §9.2 に自動失効の表を追加、「他の端末からログアウト」を P0 に
- **#74 [低]** 「セッションの期限は延ばさない」（L1667）がスライディング更新と同じ節にあり逆に読める。期限切れ文言「しばらく操作がなかったため」が 24 時間・90 日の失効に合わない → 書き分けと文言の追加
- **#75 [低]** 期限切れの確認番号・セッションを消す日次ジョブが §9.2 では P1、§6.5・§5.16 では前提 → P0 にしてバックアップと同じジョブに

### C. 個人情報・ログ・削除

- **#79 [高]** `entry_audits` の変更前後の JSON に氏名・生年月日が残り、物理削除の匿名化・5 年削除と矛盾 → 監査 JSON には生年月日を入れず、人物の物理削除時は監査の氏名も置換。保存期間を §12 に
- **#81 [高]** アカウント（`users`）の削除を誰がどう行うか未定義。外部キーで物理削除も失敗する。メールアドレスは `mail_logs`・招待・問い合わせにも残る → 削除は匿名化で行い、ログ類のメールは期間でマスク。§5.16 に「アカウントの削除」の節
- **#83 [高]** DB バックアップの暗号化・世代数・保存場所が未定義。公開 PDF と同じ R2 に全個人情報のダンプが置かれうる → 別バケット・書き込み専用トークン・クライアント側暗号化、保存期間を §12 に
