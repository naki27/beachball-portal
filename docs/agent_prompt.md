設計書 **v0.9.5** に対応。設計書 §13 に合わせて **Phase 1a（チーム基盤）→ Phase 1b（大会申込）→ Phase 1c（大会資料の掲示）→ Phase 1d（年度更新）** の 4 段階です。Phase 0（アカウントの準備・試作・計測・復元の確認）は人が行います。

## 使い方

**進め方は `p0-tasks.md` の小分けのタスクを 1 つずつ貼る形にする**（推奨）。設計書（約 388 KB）やこのファイルの A〜D を丸ごと渡すと、1 回で利用枠の大部分を使ってしまうため。

1. `p0-tasks.md` の **L-01・L-02** でリポジトリを作る。`CLAUDE.md`（下記 F）を置き、設計書は `tools/split-design.sh` で節ごとのファイル（`docs/design/`）に分ける
2. 以降は `p0-tasks.md` §3 の定型文に、タスクを 1 つ貼る。**タスクごとに `/clear`**
3. このファイルの **A〜D のキックオフは丸ごと貼らない**。フェーズの最後の仕上げのタスク（A-29・B-18・C-03・D-05）で、その「受け入れ条件」の部分だけを貼る
4. **E のステップ用プロンプト**は、対応するタスク（A-09・A-15・B-03・B-08・C-02・D-01 など）でテストを先に書かせたいときに、タスクと一緒に貼る
5. 決めておくこと: Phase 0 で **RLS を使うか**（設計書 §14.6-32）。決まっていなければ「使う」前提で進む（A-03）
6. 設計書を直したら、`docs/design.md` を差し替えて `bash tools/split-design.sh` を再実行し、E の「設計書の更新を取り込む」を貼る
7. 日程の目安（設計書 §13）: 1a は 12/4、1b は 1/22、**本番で申込を受け付けるのは 2027-01-31**、1c（大会資料）は 2/12、1d（年度更新）は 3/12（2027 年度の年度更新の受付は 4/1〜6/30）
8. **1c を始める前に、Phase 0 で決めた大会資料の配信方法（設計書 §5.9 の第 1〜3 案のどれか）を `docs/adr/` か `docs/setup.md` に書いておく**
9. デプロイは、Phase 0 の環境ができてから `p0-tasks.md` §6 の X のタスクで行う。それまではローカルだけで動作を確かめる

## A. Phase 1a キックオフ（チーム基盤）

````markdown
# 依頼: ビーチボール大会申し込みサイト — Phase 1a（チーム基盤）

## 0. まず読むもの
- `docs/design.md`（設計書 v0.9.3）を最初に通読すること。特に §3（権限と 404/403/409 の判定規則）, §4.2〜§4.5, §5.1〜§5.3, §5.10, §5.11, §5.14〜§5.16, §5.18, §5.19, §6.3, §6.5.1, §7, §8.1〜§8.3, §9.1〜§9.3, §11, §12, 付録 A・B・D。
- 本プロンプトと設計書が矛盾する場合は設計書を優先する。
- 設計書で **【確認中】【仮】** と書かれた箇所は、書かれている内容で実装し、あとで差し替えやすい形にする（値は設定か定数の 1 か所に置く）。
- 判断が必要になったら、勝手にスコープを広げず `docs/adr/` に記録する。

## 1. ゴール
登録のチームの代表者がメールの確認番号でログインし、チームを作り、選手一覧（氏名・ふりがな・生年月日・性別）を管理し、選手を招待できる状態を、Dev Container（`.devcontainer/`）でローカルに再現できる形で作る。あわせて、テナント（協会）の分離、運営管理者によるテナントの作成とテナント管理者の招待、問い合わせフォーム、プライバシーポリシー・利用規約のページ、アカウントの管理（メールアドレスの変更・削除）を作る。

**大会・申込（1b）、大会資料の掲示（1c）、年度更新（1d）は今回は作らない。2 段階認証は P1 なので作らない。**

## 2. 技術スタック（固定。変更する場合は理由を ADR に書いて私に確認）
- Next.js（App Router）+ TypeScript（strict）、pnpm
- PostgreSQL 16 + pg_trgm + citext、Drizzle ORM（マイグレーションは drizzle-kit）。本番は Neon（シンガポール）
- 認証: 自前の**メール確認番号（6 桁）**（設計書 §9）。**マジックリンク・外部 IdP・Auth ライブラリは使わない**
- メール: `MailSender` インターフェース（local は Mailpit、本番は Brevo）。確認番号のメール以外は、送信待ちの表（`mail_logs`）に業務と同じトランザクションで積み、送信ジョブで送る（§11）
- UI: Tailwind CSS。**色は最初から CSS 変数（デザイントークン）で指定する**（P1 で協会ごとの色に差し替えるため・§5.17）。スマホ幅 375px 基準
- テスト: Vitest（ユニット）、Playwright（E2E。WebKit 375×667 と Chromium 360×640）
- ローカル: Dev Container（`.devcontainer/`。Linux のコンテナで、Postgres + Mailpit も同じ compose で起動する。手順は `docs/setup.md`）
- 本番: Cloud Run・Cloud Run Jobs（シンガポール）、Cloudflare R2。デプロイの仕組み（§6.6）は Phase 0 で人が用意したものに合わせる

## 3. スコープ（今回やること。この順で小さく進める）
1. **雛形・DB・seed**: DB のロール（`pnpm db:roles`）、マイグレーション（付録 A の DDL のうち 1a で使う表。**2 段階認証の表は作らない**）。seed で早良区協会（`sawara`）と部門プリセット 18 件（`src/lib/presets/default.ts` から）を入れ、`SUPER_ADMIN_EMAILS` のアドレスを運営管理者として登録する（アカウントがなければ `users` を作る）
2. **テナントの土台**（§5.14・§7.0）
   - テナントに属する全テーブルが `association_id` を持ち、子は `(association_id, 親の id)` の複合外部キーで親を参照する
   - URL の先頭のスラッグで協会を決める。解決は `resolveAssociation()` の 1 か所（予約語 → 現行のスラッグ → 旧スラッグは 308 → 404）。API も `/api/[スラッグ]/…`
   - リポジトリ層は `associationId` を**省略できない型**にし、削除済みの除外を既定にする。DB を読む処理はすべて `withTenant(associationId, async (tx) => …)` の中で `BEGIN` → `SET LOCAL` → クエリ → `COMMIT`。セッション単位の `SET` は使わない
   - **RLS を使う場合**（指示がなければ使う）: ロールを `app_owner` / `app_user` / `app_job` / `app_backup` に分け、全テーブルに `FORCE ROW LEVEL SECURITY`。協会をまたいで自分の情報を集める画面は `SECURITY DEFINER` 関数（`my_association_ids()` など・付録 A）
   - 404 / 403 / 409 の判定規則（§3.1）を `src/lib/authz.ts` の 1 か所に実装する。P0 ではテナント管理者・運営管理者の権限は役割の行があれば付く（P1 で 2 段階目の条件を足せる形にする）
3. **認証**（§5.1・§5.2・§9.1〜§9.3）
   - 確認番号の発行: 試行 ID を HttpOnly の Cookie で渡し、番号は `HMAC(LOGIN_CODE_HMAC_KEY, 試行 ID + 番号)` だけを保存。件名に番号。**応答の文言と所要時間は登録済みかどうかによらず同じ**
   - 照合: その試行の番号とだけ照合、間違いは試行ごとに 5 回まで、直近 3 個まで有効、応答をそろえる
   - `users` は照合に成功した時点で作る（同意した規約の版 `TERMS_VERSION` と日時を保存）。ログイン画面に同意の一文とリンク
   - セッション: 10 日・スライディング（DB の更新は 1 日 1 回）・上限 90 日・ログアウト。戻り先の `next` は相対パスだけ
   - レート制限は DB の `rate_limits` で数える
   - **テナント管理者の同時ログインは 1 つまで**（§9.2）: 別の有効なセッションがあれば 409（`admin_session_exists`）で断り、番号は使用済みにしない。最後の操作から 30 分以上たった古いセッションは終了して受け付ける【仮】。テナント管理者のセッションだけ `last_seen_at` を 1 分に 1 回まで更新
4. **運営管理者とテナント**（§5.14）: `/platform`（テナントの一覧、件数、テナント管理者の人数）、テナントの作成（1 トランザクション）、**テナント管理者の招待**（本人が `/invitations` で承諾して有効。期限 7 日【仮】、1 協会 5 名まで、承諾したらほかのセッションを終了）と解除、テナントに切り替えて入る（記録と帯・1 時間）、協会の切り替えメニュー、`/`
5. **チーム**（§5.11）: 作成（**チーム名だけで作成できる**。「協会員の登録をするチーム」のチェックは任意で既定は外れている）、個人登録（本人の情報だけ。常に年度更新の対象）、チーム情報の編集、無効化（締切前の申込があれば代表者は 409。1a では申込がないので判定の口だけ作る）、代表者の委譲（相手が承諾して代表者になる）・解除（最後の 1 人は不可）、マイページ（§5.3）
6. **選手一覧**（§5.11・§8.3）
   - 追加は本人の情報を入力する（**サジェストは使わない**）。保存時に名寄せ（§8.3 のルール 2〜6）を行い、氏名・生年月日・性別が一致する人物が協会にちょうど 1 人いれば、その人物を選手一覧に加える
   - 「自分を選手として登録する」（招待を挟まずに自分のアカウントに紐づける）
   - **代表者の操作は「選手一覧から外す」だけ**（`left_at`・`left_by`）。外した本人は 30 分以内【仮】なら元に戻せる。誤登録の行の削除（`deleted_at`）はテナント管理者だけ
   - 入力欄の上に「ご本人（未成年の方は保護者）の同意を得て入力してください」。生年月日は和暦でも入力でき、今日時点で 15 歳未満・80 歳以上なら「◯歳で合っていますか？」を確かめる（§4.3）
7. **選手の招待**（§5.15）: 招待（3 日）・再送・取り消し、承諾時の前提の再検査、`/invitations`（選手・代表者・テナント管理者の招待）、紐づけの解除（本人・テナント管理者）
8. **問い合わせフォーム**（§5.10）: `/[スラッグ]/contact`（協会宛て）と `/contact`（協会かサイトの運営者かを選ぶ）、honeypot とレート制限、受付控えと転送のメール、管理画面の一覧（協会は `/admin`、運営者宛ては `/platform`）
9. **プライバシーポリシー・利用規約**（§5.18）: `/privacy`・`/terms`（`docs/legal/*.md` を表示）、全画面のフッタのリンク
10. **アカウントの管理**（§5.19）: メールアドレスの変更（新しいアドレスに確認番号 → 確定 → 古いアドレスに通知、ほかのセッションを終了）、アカウントの削除（代表者・テナント管理者は 409。メールアドレスを元に戻せない値に置き換え、人物との紐づけを解除）
11. **論理削除と削除済みデータ**（§5.16）: `/admin/trash` の一覧・復元・物理削除（`deletion_logs`、消した中身は記録しない）
12. **ジョブ**（§6.5.1・§11）: メールの送信ジョブ（再試行、上限で `failed`）、日次ジョブ（期限切れの確認番号・セッション・招待の処理、§12 の表に従った記録の削除、DB バックアップの呼び出し口）
13. **画面の共通部品**（§4.3〜§4.5）: ボタン・入力欄・メッセージ・「元に戻す」の帯、エラーページ（403 の 3 種類・404・409・500）、入力の一時保存、送信中の表示と二重送信の抑止。画面の文言は §4.4 の対応表に従う

## 4. やらないこと（1b 以降・P1）
大会・部門・申込・公開ページ・参加チーム一覧、サジェストと「この方ですか？」（1b）、申込一覧 CSV（1b）、人物の統合の画面（1b）、大会資料の掲示（1c）、年度更新（1d）、**2 段階認証とログイン通知（P1）**、名簿の各形式出力（P1）、トップページのカスタマイズと協会の色・ロゴ（P1）、前年度の会員名簿の取り込み（P1）、利用料（P1）、決済。

## 5. UI 要件（重要）
- 利用者の 9 割は Web 操作に慣れていない人（高齢者を含む）で、選手・代表者の画面は 9 割以上がスマホから使われる。375px 幅を基準に作り、PC は中央の 1 カラムを広げるだけにする
- 選手一覧は「選手 1 名 = 1 カード」の縦積み。横スクロールするテーブルは使わない。主要なボタンは画面下部に固定
- 内部の用語（エントリー、ステータス、セッション、脱退、テナントなど）を画面に出さない（§4.4）
- 成功・エラーのメッセージは自動で消さない。動きには必ず文字を添える。`prefers-reduced-motion` に従う（§4.5）

## 6. 受け入れ条件（すべて満たすこと）
- コンテナを開く → `pnpm db:roles` → `pnpm db:migrate` → `pnpm db:seed` → `pnpm dev` で動く。手順を README に書く
- 確認番号: 発行から 10 分で無効、1 回使うと無効、試行ごとに 5 回間違えるとその試行の番号がすべて無効。**他人の試行 ID を持たないブラウザから何回叩いても、その人の番号は無効にならない**。未登録・登録済みで応答の文言と所要時間が同じ
- セッション: 最後のアクセスから 10 日で失効し、アクセスのたびに延長。DB の更新は前回から 1 日以上たったときだけ。発行から 90 日を超えたら延長しない。ログアウトで即失効
- テナント管理者が端末 A でログインしている間は、端末 B からのログインが 409 で断られ、A は切れない。A でログアウトすると同じ番号で B から入れる。代表者は複数の端末で同時にログインできる
- テナント分離: 協会 A のアカウントで協会 B の資源の ID を URL の A の下で指定すると 404、同じ協会で権限がなければ 403。別の協会の親を指す INSERT が DB で失敗する。RLS を使う場合、`app_user` で `SET LOCAL` をしないクエリが 0 件
- テナント管理者の招待: 招待しただけでは権限が付かず、承諾すると付く。招待と違うアドレスでログインしたアカウントは承諾できない。管理者と返事待ちの招待が合わせて 5 名の協会にはそれ以上招待できない
- チーム名だけでチームを作成でき、作成者が代表者になる。代表者でない選手が選手一覧の編集 API を叩くと 403。最後の代表者は降りられない
- 同一ユーザーがチーム X の代表者かつチーム Y の選手である状態を作れ、X の選手一覧は編集でき、Y は編集できない（テストで示す）
- 氏名・生年月日・性別が一致する人物が協会に 1 人いるとき、別のチームの選手一覧に同じ人を入力しても `members` は 1 件のまま（`team_members` が 2 行）。生年月日だけが違えば別の人物になり、新しいほうが `needs_review`
- 選手を外すと `left_at`・`left_by` が入り、物理削除されない。30 分以内なら外した本人だけが戻せる。代表者は `team_members.deleted_at` を入れられない
- 招待: 3 日で期限切れ。承諾時にログイン中のアカウントの確認済みメールアドレスが招待のアドレスと一致するか検査する。同じ協会の別の人物にすでに紐づいたアカウントは承諾できず、`needs_review` になる
- 問い合わせはログインせずに送れ、協会宛ては協会の連絡先へ、運営者宛ては `CONTACT_TO` へ、転送のメールが送信待ちの表に積まれる
- `/privacy`・`/terms` は未ログインで開ける。新しく作ったアカウントに、同意した版と日時が保存される
- メールアドレスの変更: 新しいアドレスに届いた番号を入れるまで変わらない。変更すると古いアドレスへの通知が積まれ、ほかのセッションが終了する
- アカウントの削除: 代表者・テナント管理者は 409。削除すると元のメールアドレスが `users` に残らず、人物との紐づけが外れ、人物と選手一覧は残る
- `normalizeName` のユニットテストが §8.2 の例をすべて含む。名寄せのテストが §8.3 のルール 0〜7 と「ルールと記録の対応」の表をすべて含む
- 個人情報（特に生年月日）がログに出ていない。氏名・メールアドレスが URL のパスやクエリ文字列に載っていない
- §3.2 の権限表のうち 1a に関わる行を 1 か所のデータにし、テストをそこから生成している
- `pnpm lint` / `pnpm typecheck` / `pnpm test`（`TZ=UTC` と `TZ=Asia/Tokyo` の両方）/ `pnpm test:e2e` がすべて通る
- E2E（ログイン → チーム作成 → 選手を 4 人追加 → 選手を招待）が 375×667（WebKit）と 360×640（Chromium）で通り、文字 200% のスクリーンショットを保存している

## 7. 進め方
1. 最初のターンでは実装せず、「実装計画」だけを出して私の承認を待つ。計画には ファイル構成、実装順序、仮決め事項の一覧、確認したい質問 を含める
2. 承認後、上記 3 の順に小さく実装する。各ステップでテストを通してからコミット（Conventional Commits、メッセージは日本語可）
3. 判断が必要な箇所は、勝手にスコープを広げず `docs/adr/NNNN-<slug>.md` に「背景・決定・理由・却下した代替案」を 1 ファイル 1 決定で残す
4. 各ステップの終わりに「やったこと / 動作確認の手順 / 設計書の【確認中】【仮】に触れた箇所 / 次のステップ」を 10 行以内で報告する
5. 完了時に README へ 実装済み / 未実装 / 既知の課題 / 本番デプロイ手順 を追記し、`docs/ops.md` に運用の手順（テナント管理者の招待の前の本人確認、役員へのログインの案内など）を追記する

## 8. 禁止・注意
- 秘密情報をコードに埋めない（`.env.example` を用意し、実値は `.env` のみ）
- 氏名・生年月日などの個人情報をログ・エラーメッセージに出さない。URL に載せない（検索語も POST の本文で送る）
- 確認番号・トークン・セッション ID を平文で保存しない（確認番号は HMAC、ほかは SHA-256）
- **`association_id` の条件を付け忘れたクエリを書かない**。リポジトリ層と `withTenant` で強制する
- 認可はサーバー側で必ず検査する。UI の出し分けだけで済ませない
- 生年月日を含む API の応答を増やさない（代表者の自チームの選手一覧と、選手本人の情報だけ）
- 設計書にない外部サービス・ライブラリを追加する場合は ADR に理由を書く
- 生成したコードを「動くはず」で放置せず、必ず実行して確認する

## 9. 間違えやすい点（設計書から抜粋。迷ったら設計書を見る）
- アカウント（`users`）・人物（`members`）・所属（`team_members`）・代表者（`team_admins`）・本人の紐づけ（`members.user_id`）を混同しない（§5.15）
- ロールの包含（テナント管理者 ⊇ 代表者 ⊇ 選手）は認可の判定だけに使う。マイページ・申込のチームの候補・「あなたのやること」には、`team_admins` に自分の行があるチームだけを出す（§3.1）

- 登録のチーム（組織の運営・年度更新）と大会に出るチーム（その場限りも多い）は考え方が違う。個人登録では大会に申し込まない（§5.5・§5.11）

- 業務上の日付（締切・年度・年齢の基準日）は日本時間の年月日で扱い、`Date` に変換しない。「今日」は `todayInTokyo()` から取る（§7.0・付録 D）
````

````markdown
# CLAUDE.md

## プロジェクト
ビーチボール大会申し込みサイト（仮の名前。最初の協会は早良区協会）。サイト名（タブの題名・ヘッダ・メール）は `src/lib/site.ts` の `SITE_NAME` だけに書き、ほかに直書きしない。設計書は `docs/design/` の節ごとのファイル（一覧は `docs/design/index.md`。元は `docs/design.md` v0.9.5）。進み具合は `docs/progress.md`。決定記録は `docs/adr/`。運用手順は `docs/ops.md`。プライバシーポリシー・利用規約は `docs/legal/`。

## タスクの進め方（利用枠を節約するため。必ず守る）
1. タスクは 1 回に 1 つ。貼られたタスクの範囲だけをやる
2. 最初に `docs/progress.md` を読む
3. **設計書は、タスクの「読む設計書」に書かれた `docs/design/` のファイルだけを読む**。`docs/design.md`（全体）・`docs/design/00-header.md`・`docs/design/14-*.md` は読まない。「〜の部分」と書かれていたら、見出しを Grep で探してその部分だけを読む。ほかの節が必要なら、読む前に私に聞く

5. テスト・ビルドの出力は、失敗した部分だけを見る

## ローカルでの注意

## 規約
- TypeScript strict。`any` 禁止

- 判定の規則: URL の協会と資源の協会が違う・資源がない → 404／権限がない → 403（未ログインも 403。リダイレクトしない）／締切後・定員など → 409
- ロジックの単一実装を守る:
````
