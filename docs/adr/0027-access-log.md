# 0027 利用者の操作ログは proxy で 1 リクエスト 1 行に残す

## 背景

設計書には、記録として `entry_audits`（申込の変更履歴）・`mail_logs`・`export_logs`・`admin_access_logs`（運営管理者の重要操作）があるが、
**ふつうの利用者が「どの画面で何をしたか」を通しで見られる記録はない**（§12「ログ」）。

問い合わせ（「申し込んだはずなのに入っていない」「締切に間に合ったはず」）が来たときに、
その人がいつ・どの画面まで進んだのかを確かめる手段がないと、原因を切り分けられない。

## 決定

`src/proxy.ts`（すべての画面と API の前で動く）から `src/lib/access-log` を呼び、**リクエストを 1 行ずつ JSON Lines で残す**。

### 残す項目

| 項目 | 中身 |
|---|---|
| `at` | 日本時間の ISO 8601（`2026-09-21T12:34:56.789+09:00`。`formatTimestampTokyo`） |
| `method` `path` | どの画面・API か |
| `query` | 検索文字列。**値を伏せる名前の決まり**（下記）に当たるものは `***` |
| `slug` | 協会（`slugFromUrl`。`/api/…` も見る） |
| `action` | Server Action の id（`next-action` ヘッダ）。POST は画面と同じ URL なので、これが「どの操作か」の手がかり |
| `session` | セッションの SHA-256（`sessions.session_hash` と同じ値） |
| `ip` `ua` | 接続元（`x-forwarded-for` の先頭）と User-Agent |

- **応答のステータスは残さない**。proxy は後続の応答を見られないため。リクエストだけで用は足りる（依頼の通り）
- `/_next/…` と `/api/health`（死活監視が毎分叩く）は残さない

### 個人情報を入れない（設計書 §12）

- 氏名・メールアドレス・生年月日は URL に載せない決まりだが、**万一入っても残らないように**、
  `q` `query` `keyword` `key` `search` と、`code` `token` `secret` `password` `mail` `name` `birth` `tel` `phone` `address` を含む名前のクエリは値を `***` にする
- 利用者をたどるのは**セッションのハッシュ**から。ハッシュは元に戻せないので、ログが漏れてもなりすましには使えない。
  誰かを知りたいときは `select user_id from sessions where session_hash = '…'`（セッションは期限切れで日次ジョブが消すため、古いログはたどれない）

### 出力先とローテーション

`ACCESS_LOG_DRIVER` の 1 か所で切り替える（`STORAGE_DRIVER` と同じ形）。

- `file`（既定・ローカルと自前サーバー）: `logs/access.log`。**日本時間の月が変わるか 100 MB を超えたら**
  `access-YYYYMMDD-HHMMSS-NN.log` に退避し、**退避したものを 6 世代（月ごとなら半年分）残して古いものから消す**
- `stdout`（**本番の Cloud Run**）: 標準出力に出し、Cloud Logging に任せる
- `off`: 記録しない

**本番でファイルを使わない理由**: Cloud Run のファイルはインスタンスが終わると消え、スケール to ゼロ（§6.5）と複数インスタンスでは
1 本のファイルにならない。保存期間は Cloud Logging 側で 180 日に設定する（X-01）。

### 書き方

リクエストを待たせないよう、行は順番待ちの列に積んで非同期に書く。書けなくても画面は止めず、最初の 1 回だけ標準エラーに出す。

## 理由

- 問い合わせの切り分けに要るのは「いつ・誰が・どの画面に来たか」で、リクエストだけで足りる
- proxy は 1 か所で全部のリクエストを見られる。画面ごとに書き足すと必ず漏れる
- セッションのハッシュなら、氏名・メールアドレスをログに置かずに人をたどれる
- 保存期間の指定（半年）に対し、月ごと 6 世代がそのまま対応する。100 MB の上限は、
  想定（月 1 万件程度・§6.5）をはるかに超えて増えたときの歯止め

## 却下した代替案

- **DB のテーブルに残す**: 1 リクエスト 1 行の書き込みが増え、Neon の無料枠と応答時間に響く。RLS の設計も要る。調べるのは年に数回
- **応答のステータスまで残す（各 Route Handler・Server Action に書き足す）**: 書き漏れが必ず出るうえ、P0 の全画面に手を入れることになる
- **本番もファイルに書く**: Cloud Run では消える。R2 に上げる案もあるが、そのための仕組み（まとめて送る・失敗時の扱い）が要り、Cloud Logging で足りる

## 追記が要ること

- X-01 で、本番の環境変数に `ACCESS_LOG_DRIVER=stdout` を入れ、Cloud Logging の保存期間を 180 日にする
- プライバシーポリシーは「利用の記録（操作の記録・通信の記録（IP アドレスなど））」で既にこの記録を含んでいるので、変更しない
