# 0015 管理画面（チームとメンバー）の細部

## 背景

A-21 で運営（テナント管理者）のチーム管理（`/[スラッグ]/admin/teams`）とメンバー管理（`/[スラッグ]/admin/members`）を作った。設計書 §4.2 #15・#16・§10・§5.16 に書かれていない次の点を決める必要があった。

1. 「代表の付け替え」（§4.2 #16）の中身。代表者による委譲は本人の承諾が要る（§5.11）が、運営が行うときも同じか
2. 運営が使う編集・無効化の API を、代表者用と分けるか
3. 誤登録の選手一覧の行の削除に「元に戻す」を付けるか
4. メンバー管理の検索のしかたと、一覧の並び

## 決定

1. **運営の「付け替え」は承諾なし**。`POST /api/[スラッグ]/admin/teams/[id]/admins { email }` で、そのアドレスの**既存のアカウント**をすぐ代表者にする（`granted_by` = 操作したテナント管理者）。アカウントがなければ 409（本人に一度ログインしてもらう）。解除は代表者と同じ API（最後の 1 人は 409）
2. **分けない**。`PATCH /api/[スラッグ]/teams/[id]`（編集・協会員の登録をするチームか・無効化）はテナント管理者も通る（権限表の包含）。運営だけの操作（削除・付け替え・誤登録の行の削除・人物の修正）だけ `/api/[スラッグ]/admin/…` に置く
3. **付けない**。誤登録の行の削除は「なかったことにする」操作で、戻すのは `/admin/trash`（A-26）。画面では確認を挟む
4. 氏名・ふりがなの**正規化後の部分一致**（`normalize.ts`。全角・半角、ひらがな・カタカナの違いを吸収）。検索語が空なら最新 100 件を、**要確認の人物を先に**並べる

## 理由

- 1: 「付け替え」は代表者が連絡の取れない状態（退会・端末を失った）で協会が使う操作で、本人の承諾を待てない。運営の操作は記録に残る（`granted_by`）
- 2: 同じ判定（`authorizeTeam` の包含）で通るものを二重に作らない
- 3: 論理削除の復元は §5.16 で「削除済みデータ」画面に集める
- 4: 名寄せと同じ正規化を使えば、表記の揺れでも見つかる。要確認の人物は B-15 の解消の対象なので目につく所に

## 却下した代替案

- 運営の付け替えも招待（承諾）にする: 連絡の取れない代表者を外すのに、新しい代表者の承諾を待つ必要はない。一方で、運営が誤って他人を代表者にしても、その人の画面には「チームの代表者」として出るだけで個人情報の漏えいにはならず、解除で戻せる
