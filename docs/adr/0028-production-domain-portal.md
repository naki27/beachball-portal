# 0028 本番のドメインは `portal.fukuoka-city-beachball.org` にする

## 背景

設計書は本番のドメインを `entry.fukuoka-city-beachball.org` としている（§11.1・§6.3 の例）。本番の準備（`docs/deploy-prep.md` §0）で、運営者が `portal.` を選んだ。ドメインは `APP_BASE_URL`・メールのリンク・Cookie・パスキー（P1）の RP ID に効き、あとから変えると全員のログアウトとパスキーの登録し直しが要る（§11.1）。

あわせて、Cloud Run にドメインをつなぐ方法を調べた（2026-10-02・公式ドキュメント）。

| 方法 | `asia-southeast1` | 費用 | 注意 |
|---|---|---|---|
| Cloud Run のドメインマッピング | 使える（対応リージョンに入っている） | 0 円 | **プレビュー**。公式は「遅延の問題があり本番向けではない・GA にならない」としている |
| Firebase Hosting の転送 | 使える | 無料枠あり | **Cookie は `__session` という名前のものしか通さない**。いまのアプリは `__Host-session` と `__Host-login_attempt` を使うので、そのままではログインできない |
| グローバルの外部アプリケーションロードバランサ | 使える | 月 18 ドル前後から（転送ルール） | 予算アラート（月 1,000 円）を超える |

## 決定

- **本番のドメインは `portal.fukuoka-city-beachball.org`**。設計書の `entry.` は `portal.` に読み替える（設計書は次の版で直す）
- **つなぎ方は、まずドメインマッピングで始める**。H-03 の実測で、`*.run.app` とドメインマッピングの両方を測り、遅延の差が目標（通常時 1 秒以内・コールドスタート時 4 秒以内【仮】）を壊すなら Firebase Hosting に切り替える。そのときは Cookie を `__session` 1 つにまとめる作業（`src/lib/auth/cookies.ts`・`__Host-` の接頭辞をやめる）を別の ADR にする

## 理由

- 費用 0 円で、アプリのコードを変えずに始められる
- プレビューの遅延の問題が、この規模で実際に効くかは測ってみないと分からない。測ってから決めても、利用者が持つ URL（`portal.`）は変わらない
- Firebase Hosting は Cookie の制約で認証の作りに手が入る。ロードバランサは費用が予算に合わない

## 却下した代替案

- **`entry.` のまま**: 運営者が `portal.` を選んだ。公開前なので、いま変えても誰にも影響しない
- **最初から Firebase Hosting**: `__Host-` の接頭辞の守り（Domain を付けられない・Secure 必須）を手放すことになる。必要になってからにする
- **ロードバランサ**: 上の費用の理由
