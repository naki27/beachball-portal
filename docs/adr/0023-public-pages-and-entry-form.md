# 0023 公開ページと申込の入力ページの細部（公開 API の入口・「あと◯日」・ワンタイムの値）

## 背景

B-06 で公開ページ（協会トップの大会・大会一覧・大会詳細・参加チーム一覧）、B-07 で申込の入力ページの骨組みを作った。設計書 §5.6・§5.5 に書かれていない次の 5 点を決める必要があった。

1. ログインしていなくても使える協会の中の API を、権限表（`src/lib/api/permissions.ts`）でどう表すか
2. 部ごとに締切が違う大会で、一覧の「あと◯日」をどの締切から数えるか
3. 大会そのものを「受付中／今後／終了」に分ける判定をどこに置くか
4. 締切後・受付前に申込の入力ページを開いたとき、何を出すか
5. 送信用のワンタイムの値を、どこで発行してどこに持つか

## 決定

1. 権限表に **`publicTenant`** という入口の種類を足す。協会は解決するがログインは求めない（`resolveAssociationForApi` だけを通す）。§3.2 の行は `viewPublic`
2. **その大会のいちばん遅い締切**（部の上書きを含む）から数える。一覧・トップには 1 つの数字だけを出し、部ごとの締切は大会詳細で部ごとに違うときだけ出す
3. **`src/lib/deadline.ts` の `tournamentEntryState(tournament, categories, now)`**。1 つでも受け付けている部があれば「受付中」、どの部もまだなら「これから」
4. **409 の画面**（`ConflictScreen`）と問い合わせフォームへの導線。403 とは混ぜない。**テナント管理者は開ける**（§3.2）
5. **入力ページを開いたときにサーバーが発行**し、画面の入力値（一時保存の中）に持つ。**消費は B-10**（送信の処理）で行う

## 理由

- 1: 権限表は「§3.2 の行と URL の対応」を唯一のデータにしている（§12.1）。公開の API を `public`（テナント外）に混ぜると、協会の解決忘れ（別の協会の大会が見える）をテストで捕まえられない
- 2: 利用者が知りたいのは「まだ申し込めるか」。部ごとの締切を一覧に並べると、字が小さいスマホでは読み切れない（§4.3）。いちばん遅い締切にすると「あと◯日」が 0 になった時点でどの部も締め切られている、という関係が保てる
- 3: 規約「締切・受付の可否 → `src/lib/deadline.ts`」。画面ごとに「open な部があるか」を書くと、手で締め切った大会（`closed`）の扱いがずれる
- 4: §3.1 の判定規則「締切後・定員など → 409」。入力ページはログインした人なら開ける（§5.5 v0.9）ので、開けない理由は権限ではなく期間。問い合わせの導線は §5.5(d) の締切後の扱いと同じ
- 5: §5.5 は「入力ページを開いたときに発行し、送信時に消費する」と書いている。B-07 には送信がないので、発行と持ち回りだけを入れた。一時保存に入れておくと、ログインし直しても同じ値が戻り、1 つの申し込みに 1 つの値という関係が保てる

## 却下した代替案

- 公開の API を `{ kind: "public" }` にする: テナント外の API（`/api/health` など）と同じ扱いになり、協会の解決を忘れても気づけない
- 「あと◯日」を部ごとに出す: 一覧が縦に伸び、どれが自分に関係する締切か分からなくなる
- 締切後の入力ページを 404 にする: 大会は実在するので「見つからない」は誤り。§3.1 の 3 分類（404 / 403 / 409）のうち 409 が正しい
- ワンタイムの値を DB の表に持つ: 消費するときに要る表（どの申し込みで使ったか）は B-10 の設計と一緒に決めたほうがよい。B-07 で表を足すと、B-10 で作り直すことになる
- 締切後でも入力ページを開かせ、送信だけ 409 にする: 選手を全部入れてから断られるのは、書き直しの手間が大きい（§4.5 原則「先に気づけるように」）
