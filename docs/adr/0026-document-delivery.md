# 0026 大会資料の配信方法は `PUBLIC_FILES_BASE_URL` の 1 か所で切り替える

## 背景

設計書 §5.9「配信の仕組み」は、公開用バケットの配信方法に 3 つの案を挙げ、**どれにするかは Phase 0 で決める**としている。

1. R2 の公開用バケットを独自ドメイン（例: `files.entry.…`）で配信する
2. Cloudflare Workers（`*.workers.dev`）で公開用バケットを読み出して返す
3. アプリが R2 から読み出して返す

C-01・C-02 を作る時点で、この決定は `docs/adr/` にも `docs/setup.md` にも書かれていない（Cloudflare でドメインを扱えるかが未確認のため）。決まるのを待つと 2 月の大会冊子に間に合わないので、決まっていなくても進められる形にした。

## 決定

アプリは**公開用の URL の先頭（`PUBLIC_FILES_BASE_URL`）しか知らない**。3 つの案の違いはこの環境変数の値だけに現れる。

- 第 1 案 → `https://files.entry.…`（独自ドメイン）
- 第 2 案 → `https://<名前>.workers.dev`
- 第 3 案 → アプリ自身の URL（R2 から読み出して返すルートを X-05 で足す）
- ローカル → 空欄。同じオリジンの `/dev-files/…`（開発時だけのルート。`STORAGE_DRIVER=local` のときだけ動く）

利用者が共有するのは、どの案でも変わらないアプリの URL（`/[スラッグ]/tournaments/[id]/documents/[docId]`）で、そこから公開用の URL へ 302 で送る。
**配信方法を後から変えても、配った URL は開けたままになる。**

実際にどの案にするかは X-05（独自ドメイン・大会資料の配信・Brevo の送信ドメイン）で決めて、この ADR に追記する。

## 理由

- どの案でもアプリの作りが変わらないので、決定を待たずに 1c を仕上げられる
- 案 1 → 案 2 の切り替え（Cloudflare でドメインが扱えないと分かったとき）が、環境変数の書き換えだけで済む
- ローカルを「同じオリジンの `/dev-files`」にしておくと、コンテナの中（`127.0.0.1`）でも Mac のブラウザ（`localhost`）でも同じように開ける

## 却下した代替案

- **案を 1 つに決めて作り込む**: Cloudflare でドメインを扱えるかが未確認のうちに決めると、外れたときに作り直しになる
- **アプリが常に R2 から読み出して返す（案 3 に固定）**: 大会冊子は拡散されて何度もダウンロードされうる。Cloud Run の転送量に課金されるため、費用が読めない（§5.9）
