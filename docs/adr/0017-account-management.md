# 0017 アカウントの管理（メールアドレスの変更・削除）の細部

## 背景

A-24・A-25 でメールアドレスの変更（`/mypage/email`）とアカウントの削除（`/mypage/delete`）を作った。設計書 §5.19・§9.2 に書かれていない次の点を決める必要があった。

1. メールアドレスの変更の確認番号を、ログインの照合とどう共通化するか
2. 削除の確認に使う「確認番号の再入力」は、どの用途（`login_codes.purpose`）の番号か
3. 削除は協会をまたぐ（人物の紐づけ・招待）のに、テナントの表は RLS の下にある。どう実行するか
4. 削除したアカウントのメールアドレスを何に置き換えるか
5. 削除できない理由を、画面にいつ出すか

## 決定

1. 番号を照らし合わせる規則（試行の Cookie に紐づける・直近 3 個・5 回まで・失敗の数え方）を **`src/lib/auth/match-code.ts` の 1 か所**にし、ログインの照合（`verify-login-code.ts`）とメールアドレスの変更（`account/email-change.ts`）の両方がそこを通る。メールアドレスの変更では `purpose = 'email_change'` と `user_id` で絞る
2. 削除の確認は、**いまのメールアドレス宛ての `purpose = 'login'` の番号**（画面は `POST /api/auth/request` を呼ぶ）。確定するときに「その番号がいまのアドレス宛てか」を確かめる。削除のためだけの用途を増やさない（`login_codes.purpose` の check は `login` と `email_change` だけ）
3. 削除の本体は **`SECURITY DEFINER` 関数 `delete_my_account(new_email)`**（マイグレーション 0009）。対象は `current_user_id()` だけで、引数でほかの人を指定できない。所有者の `app_definer` に、この関数が書く表（`members`・`team_invitations`・`association_admin_invitations`・`users`・`sessions`・`login_codes`）の権限だけを足す。アプリのロール（`app_user`）の権限は変えない
4. `deleted-<ランダム>@deleted.invalid`。`users_email_uk` は削除済みを除いた一意制約なので、**同じアドレスで作り直せる**。`.invalid` は規格で「存在しないことが保証される」トップレベルドメイン
5. **画面を開いた時点で出す**（`my_account_deletion_block()`）。理由があるときは確認番号のボタンも出さない。API（`DELETE /api/me`）でも同じ検査をして 409 を返す

## 理由

- 1: 番号の規則が 2 か所に分かれると、片方だけ直したときに上限やロックの扱いがずれる（§9.2 は総当たり対策の細部まで決めている）
- 2: 削除は「いま本人が操作している」ことの確認で、ログインと同じ強さでよい。用途を増やすと `login_codes` の検査が増える
- 3: 協会をまたぐ操作は `SECURITY DEFINER` 関数に閉じる（§5.14 と 0003 の方針）。アプリ側で協会ごとに `withTenant` を回すと、役割を持たない協会に届いている招待（招待された人はまだその協会と関係がない）に手が届かない
- 4: メールアドレスを消すだけ（null）にすると、送信の記録や問い合わせとの突き合わせで元のアドレスが復元できてしまう。置き換えれば「元に戻せない」（§5.19）
- 5: 押してから断られるより、開いた時点で理由と次の手順が出るほうが迷わない（§4.5）
