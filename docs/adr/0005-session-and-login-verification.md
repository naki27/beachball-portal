# 0005 セッションの Cookie の期限と、確認番号の照合で決めたこと

## 背景

設計書 §9.2 はセッション（10 日のスライディング・90 日の上限・DB を書くのは 1 日 1 回）と確認番号の照合（試行 ID・直近 3 個・5 回まで）を決めている。実装で決めが要ったのは次の点。

1. スライディング更新のたびに「Cookie の `Max-Age` も更新する」とあるが、Next.js の Server Component（ページの描画）からは Cookie を書き換えられない
2. 「1 つの試行につき、間違いは合計 5 回まで」の数え方（`login_codes.attempt_count` は行ごとの列）
3. 戻り先の ③「役割を持つ協会が 1 つだけならその協会のトップ」の数え方
4. ログアウトのときの一時保存（`localStorage`）の消し方

## 決定

1. **セッションの Cookie の `Max-Age` は 90 日（発行からの上限と同じ）にし、有効期限は DB の `sessions.expires_at` を正とする**。10 日のスライディング（1 日 1 回の更新）は `loadSession()` が DB だけで行う。Cookie が DB より長く残っても、DB の期限が切れていれば「セッション切れ」の 403 になるだけで、ログイン状態にはならない
2. **間違えた回数は試行の単位で数え、その試行の未使用の行すべての `attempt_count` に同じ値を書く**（最大値を「これまでの回数」とする）。5 回目で試行の番号をすべて `used_at` で無効にする。照合の失敗は加えてメールアドレス単位（10 回/時）・IP 単位（30 回/時）で `rate_limits` に数える
3. **`my_association_ids()`（`SECURITY DEFINER`）を `app.user_id` だけを `SET LOCAL` したトランザクションで呼ぶ**。1 つならその協会のスラッグへ、それ以外は `/mypage`
4. **ログアウトのボタン（クライアント）が `clearAllDrafts()` を呼んでから `POST /api/auth/logout` を送る**。サーバーはセッションの行を消し、Cookie を空にする
5. テナント管理者の同時ログインの制限（409・30 分の逃げ道・`last_seen_at` を 1 分に 1 回）は A-10 で `verifyLoginCode()` と `loadSession()` に足す

## 理由

- 1: Route Handler と Server Action 以外では `Set-Cookie` を返せない。ページの描画のたびに API を呼ばせるより、DB を正にするほうが単純で安全側（Cookie の残りが長くても DB が切れていれば入れない）
- 2: 番号ごとに数えると、再送で番号を増やすほど試せる回数が増える。試行の単位で数えれば、設計の「試行につき 5 回」のとおりになる
- 3: RLS の下で協会をまたいで役割を数える方法は、設計書 §5.14 のとおりこの関数だけ
- 4: 一時保存は生年月日を含むので、サーバーの処理の成否にかかわらずブラウザ側で先に消す

## 却下した代替案

- proxy（middleware）でセッションを読んで Cookie を延長する: proxy は DB に触らない決まり（ADR 0003）
- スライディングのたびに Server Action で Cookie を書く: すべてのページで書き込みの往復が増え、描画が遅くなる
