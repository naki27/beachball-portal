# 0021 大会の管理の細部（状態の呼び名・入力の形・整合性の検証の置き場所）

## 背景

B-04 で大会の管理（`/[スラッグ]/admin/tournaments`・作成・編集・状態の変更）を作った。設計書 §5.4・§4.2 #13 に書かれていない次の 4 点を決める必要があった。

1. 状態（`draft` / `open` / `closed` / `archived`）を画面にどう出すか。§4.4 の対応表にこの行がない
2. 日付と数の入力を、画面とサーバーのどちらで検査するか
3. 「設定値の整合性」のうち表をまたぐもの（参加人数の下限 ≧ 部のコート人数、部の締切 ≧ 申し込みの開始）をどこで検証するか。B-04 の時点では部を作る画面がない（B-05）
4. 大会の削除（論理）をこのタスクで作るか

## 決定

1. **`TOURNAMENT_STATUS_LABEL`（`src/lib/tournaments/tournament-input.ts`）の 1 か所**に置き、「準備中（公開しない）」「受付中（公開する）」「受付を終了（公開する）」「終了した大会」と出す。内部の値は画面に出さない
2. **`parseTournamentInput` を画面とサーバーの両方で使う**（`team-input.ts` と同じ形）。画面は入力値を文字列のまま持ち、日付・数への変換とすべての検査をこの関数だけが行う。エラーは欄の名前（`field`）付きで返し、API も同じ `field` を返して該当の欄の下に出す
3. **サービス層（`src/lib/admin/tournaments.ts` の `assertConsistentWithCategories`）で検証し、違反は 409**。部が 1 つもなければ何も見ない。B-05 で部を足す側からも同じ関数を呼べるようにしておく
4. **作らない**。一覧・作成・編集・状態の変更だけにし、削除（論理）と削除済みデータの扱いは B-17 でまとめて入れる

## 理由

- 1: `CLAUDE.md` の規約「内部の用語を画面に出さない」。§4.4 に行がないので、対応表に足す代わりにコードの 1 か所に置いた（設計書を差し替えるときに §4.4 へ移す）。「公開しない／公開する」を添えたのは、`closed` が「公開はするが申し込めない」という分かりにくい状態だから
- 2: 同じ検査を 2 か所に書くと必ず食い違う。`type="date"` と `type="number"` に頼ると、対応していない端末や API 直叩きで抜ける
- 3: 部の設定値（`category_presets.court_size` など）は別の表なので DB の CHECK では書けない（付録 A も「大会の保存時にアプリで検証する」と書いている）。判定を先に入れておけば、B-05 で部を足すときは呼ぶだけで済む。締切後・定員などと同じ「業務上の条件」なので 409（§3.1 の判定規則）
- 4: 申込が付いた大会を消す扱い（`entries` の cascade・`deletion_logs`）は B-17 の範囲で、そこと切り離して作ると二度手間になる

## 却下した代替案

- 状態ごとに別のボタン（「受付を始める」など）を置く: §5.4 は状態を 4 つの値として持つと決めており、編集の画面で選ぶ形が最も素直。押し間違いの取り消しも同じ画面でできる
- 参加人数の下限の検証を 400 にする: 入力の形は正しく、部の設定との関係で受け付けられないだけなので 409（§3.1）
- 一覧を公開ページと共通の部品にする: 公開ページは B-06 で条件（`draft` は出さない・過去の大会は別の枠）が違う
