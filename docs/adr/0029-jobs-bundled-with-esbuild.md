# 0029 本番のジョブは esbuild で 1 ファイルにまとめて動かす

## 背景

定期ジョブ（`src/jobs/mail.ts`・`daily.ts`）とマイグレーションは、ローカルでは `tsx`（devDependencies）で TypeScript のまま動かしている。本番は Cloud Run Jobs で動かす（X-02・X-03）。動かし方は 2 つ考えた。

- A: 本番のイメージに `tsx` を入れ、いまと同じく `tsx src/jobs/*.ts` で動かす
- B: esbuild で 1 ファイルにまとめ、`node dist/jobs/*.mjs` で動かす

## 決定

**B にする。**

- esbuild は `tsx` が中で使っているものを使い、新しい依存は足さない
- まとめるのは `src/jobs/*.ts` とマイグレーションのスクリプト（`src/db/scripts/migrate.ts`）。`@/` の解決は tsconfig から読む。ネイティブのモジュールなど、まとめられないものは外に残してイメージに入れる
- **CI で、まとめたファイルを実際に動かす**（使い捨ての DB で `job:mail` と `migrate` を 1 回ずつ）。ローカル（tsx）と本番（まとめたファイル）のずれを、ここで見つける
- 実行時にファイルを読む処理は、まとめたあとの置き場所でも読めるようにする（見つかったら直す）
- Artifact Registry に古いイメージを消すルールを入れる（無料枠 0.5 GB）

## 理由

- イメージが小さく起動が速い。メールのジョブは数分おきに起動するので、毎回のイメージの取得と TypeScript の変換の時間が効く
- Artifact Registry の無料枠（0.5 GB）に収めやすい
- 本番に入るパッケージが少なく、攻撃の入口が減る
- esbuild は型を検査しないが、CI の `pnpm typecheck` で拾える

## 却下した代替案

- **A（本番に tsx を入れる）**: ローカルと同じに動く利点はあるが、`node_modules` をほぼ丸ごと持ち込むのでイメージが数百 MB になり、上の理由に合わない
