# 0018 削除済みデータと物理削除の細部

## 背景

A-26 で「削除済みデータ」（`/[スラッグ]/admin/trash`）と物理削除を作った。設計書 §5.16 に書かれていない次の点を決める必要があった。

1. 表ごとの扱い（一覧・復元・一緒に消えるもの）をどこに置くか。1b・1c の表をあとから足せる形にする
2. 一緒に消える行を、アプリで消すか、外部キーの `on delete cascade` に任せるか
3. 親が削除済みのままの子（削除されたチームの選手一覧の行）を復元できるか
4. 1a では、まだ物理削除できないものをどう断るか（申込まわりは B-01・B-17）
5. 問い合わせ・人物の**論理**削除は誰がどこで行うか（A-22・A-21 では画面がなかった）

## 決定

1. `src/lib/admin/trash.ts` の `TRASH_TABLES` に**表ごとの定義を 1 か所**（呼び名・一覧・件数・復元・物理削除）。画面と API はキー（`teams` / `team_members` / `members` / `contact_messages`）だけを受け取り、表ごとの分岐を持たない。1b・1c の表はここに足す
2. **外部キーの cascade に任せる**（`members` → `team_members`・`member_aliases`・`team_invitations`、`teams` → `team_members`・`team_admins`・`team_invitations`）。`deletion_logs.cascaded_count` のために、消す前に件数だけ数える
3. **復元させない**（409）。一覧にも理由を出す（「チームが削除されています。先にチームを復元してください」）。親を復元してから子を復元する
4. **409 で断り、理由を画面の言葉で出す**。1a では「申し込みに出ている方（`members.entry_count > 0`）」「申し込みが残っているチーム」「ほかの登録のまとめ先になっている人物」を断る。`entry_players` の書き換え（§5.16 の保存期間／本人の依頼の作り分け）は B-17
5. **論理削除はその画面で**: 問い合わせは `/admin/contacts` の「削除する」（`manageContacts`）、人物は `/admin/members/[id]` の「この登録を削除する」（テナント管理者）。復元と物理削除だけを `/admin/trash` に集める

## 理由

- 1: 対象の表はこれから 10 個以上に増える（§5.16 の一覧）。画面・API・テストが表ごとに増えないようにする
- 2: アプリで消す順番を間違えると外部キー違反か消し残りになる。付録 A の `on delete` を正とし、コードはそれに合わせる（§5.16「外部キーの削除時の動作はこの表に合わせる」）
- 3: 子だけ復元すると、削除済みの親にぶら下がる行ができて一覧から見えない（直す手段が DB しかなくなる）
- 4: 「まだできない」を黙って成功させない。理由が画面に出れば、B-17 までの間も運用で判断できる
- 5: 削除は「その画面で見ているもの」に対して行うのが分かりやすい。ゴミ箱は集める場所に徹する
