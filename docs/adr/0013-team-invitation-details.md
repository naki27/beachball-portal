# 0013 選手の招待の細部

## 背景

A-19 で選手の招待（`src/lib/teams/invitations.ts`・`src/lib/invitations/team-respond.ts`）を作った。設計書 §5.15・§11 に書かれていない次の点を決める必要があった。

1. 招待の画面（`/invitations`）に「選手（山田太郎）として」と出すための人物の氏名を、どこから取るか
2. 「すでに別の登録と結びついています」で承諾させないとき、招待の行と人物の状態をどうするか
3. 紐づけの解除の API と、個人登録がある人の解除
4. 無効化したチームへの招待・承諾
5. 代表者としての招待（`kind = admin`）の承諾の中身（A-20 の範囲だが、同じ関数で扱う）

## 決定

1. **`my_pending_invitations()` を作り直し（0007）、`team_id` と `member_name` を返す**。返す条件（ログイン中のユーザーの確認済みメールアドレス宛ての返事待ちだけ）は変えない
2. **招待は `pending` のまま残し、招待の人物を `needs_review` にして 409 を返す**。この更新は例外で巻き戻さず確定させる（トランザクションの中で結果を返してから投げる）。テナント管理者が 2 つの人物をまとめれば（§5.8・B-15）、まとめた人物にアカウントが紐づくので招待し直さなくてよい
3. **`DELETE /api/[スラッグ]/members/[memberId]/link`**。本人（`members.user_id` が自分）とテナント管理者だけ（それ以外は 403）。**個人登録がある人は本人からは解除できない（409）**。マイページの協会の枠に「アカウントとの結びつきを解除する」を置き、確認を挟む
4. **無効化・削除したチームでは招待・再送できない（409）。承諾もできない（409）**。無効化のときに返事待ちの招待を取り消すのは A-20（`cancelOpenTeamInvitations`）
5. 承諾で `team_admins` に行を入れる（`granted_by` = 招待した代表者）。すでに代表者ならそのまま承諾扱い。移動先はチームのページ

## 理由

- 1: RLS の下の `members` を横断で読む方法は `SECURITY DEFINER` 関数だけ（§5.14）。関数の戻り値の型が変わるので作り直す
- 2: §5.15 は「承諾させず、運営の確認対象にする」「行き止まりにしない」と書いている。招待を無効にすると、まとめたあとに招待し直しが要る
- 3: §3.2「紐づけの解除は本人とテナント管理者」。個人登録は本人の人物を前提にしているため、解除すると登録情報が誰のものか分からなくなる
- 4: §5.11「無効化・削除したチームの扱い: 返事待ちの招待はすべて取り消す」に合わせ、その間の新しい招待も止める

## 却下した代替案

- 招待の画面の氏名を、招待の API の応答に持たせて画面で覚えておく: `/invitations` は一覧なので、一覧を返す関数に列があるほうが単純
- 2 で招待を `rejected` にする: 本人の操作ではない
