# 0001 seed の実行ロールと、表ごとの権限を付ける時期

## 背景

A-01 で基盤のテーブルと seed（早良区協会・部門プリセット・運営管理者）を作った。設計書は seed の中身（付録 A「初期データ」）と、ロールの分け方（§5.14「漏れを機構で防ぐ」3・§6.3）を決めているが、次の 2 点は書いていない。

1. seed をどのロールで実行するか
2. 表ごとの `grant`（`app_user` / `app_job` / `app_backup`）をどのタスクのマイグレーションで付けるか

## 決定

1. **seed は `app_owner`（`MIGRATION_DATABASE_URL`）で実行する**。`pnpm db:seed` はマイグレーションと同じ手順の一部として扱う（ローカルは `db:migrate` の直後、CI も同じ順。本番は §6.6 の「migrate」ジョブに含める予定・X のタスクで決める）
2. **表ごとの `grant` は RLS のポリシーと同じマイグレーションで付ける（A-03）**。A-01・A-02 で作る表には権限を付けず、`app_user` はそれまで表を読まない。`pnpm db:roles` が付けるのは DB への接続と `public` スキーマの利用（`app_owner` だけ作成も）までにする

## 理由

1. `platform_admins` は「seed スクリプトでのみ登録する」（付録 A）ので、アプリ用の `app_user` に書き込み権限を付けずに済む。seed が表の所有者で動けば、権限の付与を待たずに空の DB からデータを入れられる
2. 権限を先に付けると、RLS が入るまでの間に `app_user` が全協会の行を読める状態ができる。付与と RLS を 1 つのマイグレーションにまとめれば、その状態が生じない。`grant` を忘れた表は権限エラーになり、安全側に倒れる（§5.14「漏れを機構で防ぐ」の考え方と同じ）

## 却下した代替案

- seed を `app_user` で実行する: `platform_admins` への insert 権限をアプリのロールに付けることになり、付録 A の「画面からは付与できない」を機構で守れない
- `pnpm db:roles` で `alter default privileges` により新しい表に自動で権限を付ける: 付け忘れが起きない代わりに、RLS を張り忘れた表が全協会から見える（危険側に倒れる）
