# 0024 申込の送信（ワンタイムの値の持ち方・確認ページ・完了ページ）

## 背景

B-10 で申込の送信（§5.5(c)）を作った。設計書 §5.5・§5.7 に書かれていない次の 4 点を決める必要があった。

1. 「入力ページを開いたときに発行し、送信時に消費する」ワンタイムの値を、どこに持つか（ADR 0023 の 5 で B-10 送りにしていた）
2. 「入力 → 確認 → 完了」の 3 ページのうち、確認ページが入力内容をどこから読むか
3. 完了ページをどの URL にするか（§5.7 は「申込の確認・変更ページ `/[スラッグ]/entries/[id]`」の URL をメールに載せると書いている）
4. 送信が断られたときに、理由をどうやって入力ページまで運ぶか

## 決定

1. **`entries.submit_token`（uuid）に持ち、`(association_id, submit_token)` の部分一意インデックスで二重送信を止める**。送信のとき、まず同じ値の申込があるか見て、あればそれを返す（`alreadySubmitted`）。別表は作らない
2. **確認ページは一時保存（localStorage・§4.3）を読む**。サーバーからは大会名・部の名前・基準日だけを渡す。確認ページは新しい値を作らない
3. **完了ページは `/[スラッグ]/entries/[id]`**（`?done=1` で「完了」の表示にする）。B-12 の変更・取消はこの同じページに足す
4. **`sessionStorage` に理由を 1 回だけ置いて入力ページが読む**。読んだら消す。URL には載せない

## 理由

- 1: 二重送信を止めるのは DB の制約がいちばん確実（Cloud Run は複数インスタンスで、アプリの中の記憶は効かない）。別表にすると「表には入ったが申込の挿入で失敗した」という食い違いが起きうるが、同じ行の列なら起きない。連打・「戻る」からの再送のどちらも、同じ値なら 1 件目が返る
- 2: 確認ページは「入力に戻って直す」で何度も往復する（§5.5）。サーバーに下書きを置くと往復のたびに書き込みが要る。一時保存はすでに §4.3 の仕組みがあり、ログインし直しても戻る
- 3: §5.7 が完了画面に載せる項目（申込番号・大会名・部・チーム名・選手一覧・締切・変更方法）は、確認・変更ページの項目と同じ。2 つ作ると片方だけ直す事故が起きる。メールのリンク先も 1 つで済む
- 4: 理由には選手の氏名が入りうる（「◯◯さんはこの部の対象ではありません」）。URL に載せるとリクエストログに残り、§12 に反する。タブを閉じれば消える `sessionStorage` なら端末にも残らない

## 却下した代替案

- ワンタイムの値を別表（`entry_submissions`）に持つ: 申込と 2 か所を同じトランザクションで合わせる必要があり、列 1 つで足りるものを分ける利点がない
- 送信前に「処理中」の行を作って予約する: 途中でやめた人の行が残り、掃除のジョブが要る
- 確認ページをサーバーの下書き表で持つ: 往復のたびに書き込みが要り、生年月日をサーバーに一時保存することになる
- 確認ページを入力ページの中の画面切り替えにする: ブラウザの「戻る」が確認ページに戻らないため、§5.5 の「完了後に戻って再送」の道筋を確かめられない
- 完了ページを `/tournaments/[id]/entry/complete` にする: §5.7 の「確認・変更ページの URL をメールに載せる」と 2 つの URL ができ、内容が重なる
- 断られた理由を URL のクエリで渡す: 氏名がリクエストログに残る（§12）
